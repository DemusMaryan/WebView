## Що вже працює

Користувач через браузер завантажує записане монокулярне відео та явне калібрування. PostgreSQL зберігає задачу; dispatcher через Nginx передає її незалежному compute. Окремий дочірній worker декодує RGB та запускає перевірений ORB-SLAM3. До завершення доступні справжні snapshot, відповідний кадр, розріджена карта й траєкторія. Є історія, готовий результат, скасування та timeout. Відсутні пози залишаються null, прогалини й межі карт/сегментів не з'єднуються, масштаб відносний.

Підсумок є знеособленим: без паролів, токенів, рядка підключення БД чи персональних шляхів. Далі `$CV_ROOT` — наявне `~/.local/share/monotrajectoryweb`, `$DATA` — `$CV_ROOT/web`. Великі матеріали залишаються поза Git у native WSL; фізичний VHDX нині використовує диск C:, тому Linux df і запас Windows перевіряються окремо.

### Чому pending, list limit і reserve не закривають R3

У `backend/mtw/api.py:create_job` SQL count має `status.not_in(TERMINAL)`. Термінальні succeeded/failed/cancelled/timed_out не враховуються. `GET /api/jobs` повертає останні 50 (можна 1–100), але не забороняє створювати нові після цього й не видаляє старі. UI читає перші 50; зі зростанням історії потрібна пагінація. Storage reserve захищає вільне місце, cleanup забирає лише робочі PNG нових задач; обидва механізми залишають записи, відео та результати. Загального count cap і автоматичного retention цих матеріалів немає.

### Межі балансування й додаткових частин

Nginx містить два upstream server, але dispatcher захищений єдиним advisory lock, не резервує нову задачу, поки є running/dispatching, і чекає HTTP `/execute`. Другий compute у цей час може бути вільний, хоча наступна задача вже стоїть у черзі. Health та різні server_id підтверджують інфраструктуру, а не R5. Немає автоматичного запуску третього, динамічної реєстрації чи доказу обмеження масштабу. Роль/БД PostgreSQL і пароль її підключення також не є авторизацією користувача вебзастосунку.

## Упорядкований залишок для повної роботи й додаткових балів

Це план наступних окремо дозволених етапів, а не виконані функції. «День 2» — логічний наступний етап; початковий календар уже минув.

1. **R5, найважливіша вимога:** узгодити dispatcher і два compute slots, не допускаючи подвійного запуску/втрати reservation. Перевірити дві різні реальні задачі через Nginx із перекриттям саме обчислювальних інтервалів, журналами job/server/PID та двома коректними результатами; health недостатньо.
2. **Завершення користувацького сценарію R3:** загальний ліміт усіх збережених задач з атомарною відмовою, читання старішої історії з пагінацією; не видаляти 29 захищених задач і не підміняти ліміт reserve/cleanup. Після власності — окремі користувацькі квоти; політику старих задач погодити явно.
3. **R4:** реальний вхід/вихід, користувачі та owner; обмежити всі job/preview/artifact/cancel маршрути й історію. Тести анонімного доступу та двох різних користувачів. Не призначати старі задачі вигаданому спільному акаунту.
4. **Регресія R1–R3/R5:** граничні ліміти, duplicate/crash/restart, cancel і timeout зі звільненням обох слотів після змін; контролювати backing reserve. Поточний справний CV не перебудовувати. Це перевірка нової моделі виконання, а не повтор усіх старих запусків.
5. **HTTPS, додаткові бали R4:** TLS на погодженій адресі з коректною довірою сертифікату та перевіркою захисту сесії; локальний HTTP теперішнього прототипу цього не доводить.
6. **R6:** довести постановку в чергу за зайнятості всіх реальних слотів, показати приблизний ETA з вимірювань і стан очікування, зберегти обмежену чергу/429 та виключення queue time з execution cap.
7. **R7:** спочатку закрити питання ВМ/контейнерів із вихідної умови за чинного рішення без Docker. Потім автомасштабування з верхньою межею (проєктно 3), readiness і реальною задачею на новому сервері; перевірити неможливість перевищити межу.
8. **R8:** захищена адмінпанель з усіма серверами, живими процесами/задачами, CPU/RAM і чергою; перевірити відмову звичайному користувачу й актуальність метрик.
9. **Фінальне приймання:** для кожного R1–R8 зберегти факт/команду/результат, перевірити відтворення підготовленого середовища й актуалізувати звіт. Окремої обіцянки точного бала без критеріїв викладача немає.
