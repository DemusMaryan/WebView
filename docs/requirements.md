Пункти 1–5 — основа завдання; HTTPS і пункти 6–8 у вихідній умові дають додаткові бали. План проєкту охоплює всі R1–R8. Базові 2 та максимальні 3 compute-сервери — проєктні налаштування; вихідна умова вимагає щонайменше 2 сервери для балансування, але не задає максимум 3. PostgreSQL, API, dispatcher, Nginx і два HTTP compute реалізовані нативними процесами; Docker/Compose не використовуються. Промпт 3 виконує лише одну задачу одночасно; повне R5 залишається наступним окремим етапом.

Результат теми: оцінена траєкторія камери та розріджені 3D-точки із записаного монокулярного відео, у відносному масштабі. Живий потік, повторна локалізація у збереженій кімнаті та щільна фотореалістична модель не входять у межі проєкту.

## Докази Промпта 3, 02.11.2026

- R1: справжні corrupted/frame/duration/resolution/calibration помилки; HTTP 413 для file/body/chunked caps. Native timeout 45 с завершив worker і mono_export за 45,039 с; обидва слоти вільні. Вісім unittest пройшли, включно з перевіркою переповнення backing volume при вільному virtual FS.
- R2: задача `e8688279-ad66-42af-b7ec-3ce672547406` на compute-2 дала 52 різні frame_id під час роботи. 798 JSONL-записів, 688 валідних live-поз, 110 null; Twc, tracking state, сегменти й прогалини збережені. API snapshot максимум 77 682 байти, GET стану максимум 0,0143 с у цьому E2E. На момент Промпта 3 frontend ще не було.
- R3: POST 202 за 0,140 с; list/state/snapshot/result/cancel перевірені. Cancel під час tracking зупинив PID 803/839 за 0,694 с. Після зупинки/старту всіх власних сервісів і PostgreSQL результат тотожний, queued job збережений. owner_id явно null, права й користувацькі квоти не реалізовані.
- R5: dispatcher → Nginx:8081 → compute, різні server_id, реальний mono_export і артефакти. Одночасність обмежено однією задачею; критерій двох паралельних серверів не виконаний.
- R6: 10 pending прийняті, 11-та отримала 429; queued-cancel перевірено. Очікування 8,401 с не включилося в execution cap 1 с. ETA ще немає.

R4, R7 і R8 залишаються запланованими. Повний журнал HTTP, job_id/server_id, час, калібрування й відкриті питання — у [звіті backend-прототипу](backend-prototype.md). Немає автоматичного retention медіа; storage reserve зупиняє приймання/обчислення при нестачі місця.

## Докази Промпта 4, 02.11.2026

- R2: через Chrome/Playwright створено реальну задачу `73b7ec4a-fb2d-4ee2-b827-5daf0e55abac`; до завершення UI показав 51 різний frame_id і 50 різних наборів точок. Перевірено відповідність RGB-кадру та snapshot, 798 кадрів, 685 валідних live-поз, 438 фінальних поз і 2758 точок. Null, прогалини й сегменти збережені, координати відносні.
- R3: перевірені браузерні створення/історія/cancel/результат/reload, видимі помилки неправильного JSON, пошкодженого відео, timeout і неіснуючої задачі. Після cleanup збережені preview успішної та скасованої задачі відкриваються; усі початкові 29 записів і їхні файли збережено. Користувацькі права/квоти ще не реалізовані.
- Ресурси UI: snapshots обмежені, raw JSONL не опитується; геометрія перевикористовується. Закриття активного перегляду припинило polling і звільнило WebGL buffers. Backend отримав лише мінімальний preview/cleanup для нових задач після припинення процесів; storage manager/retention старих результатів не додавався. Резерв C: 5 GiB залишився.
- Фінальний frontend build, 4 frontend unit-тести, 14 backend unittest і повне браузерне приймання пройшли. Деталі, screenshot, обмеження та команди — у [звіті frontend](frontend-prototype.md). R4/R5/R6–R8 не оголошуються завершеними через появу UI; ці докази передують аудиту Промпта 5.

## Уточнення аудиту Промпта 5

У БД 33 задачі, owner_id не заданий у жодної. `create_job` рахує тільки статуси поза TERMINAL, тому успішні, помилкові, скасовані й timed_out записи не витрачають 10 pending slots. `GET /api/jobs?limit=50` (максимум 100) обрізає відповідь, а не кількість записів у PostgreSQL; пагінації старішої історії немає. Резерв диска та cleanup робочих PNG також не є загальним лімітом задач.

Dispatcher тримає один глобальний слот і чекає завершення `/execute`; черга може очікувати навіть за вільного другого compute. ETA серіалізується як null. Автоматичного запуску/реєстрації серверів та runtime-обмеження для такого розширення немає: максимум 3 поки є лише планом. `scripts/status` і health дають службовий стан, але не замінюють захищену адмінпанель із CPU/RAM та всіма процесами. Автентифікація, перевірки owner та HTTPS не реалізовані. Конкретні файли доказів і порядок завершення — у [day1-report.md](day1-report.md).
