Пункти 1–5 — основа завдання; HTTPS і пункти 6–8 у вихідній умові дають додаткові бали. План проєкту охоплює всі R1–R8. Базові 2 та максимальні 3 compute-сервери — проєктні налаштування; вихідна умова вимагає щонайменше 2 сервери для балансування, але не задає максимум 3. PostgreSQL, API, dispatcher, Nginx і два HTTP compute реалізовані нативними процесами; Docker/Compose не використовуються. Історичний Промпт 3 мав один запуск; поточні два слоти й приймання R5 описані в [parallel-processing.md](parallel-processing.md).

Результат теми: оцінена траєкторія камери та розріджені 3D-точки із записаного монокулярного відео, у відносному масштабі. Живий потік, повторна локалізація у збереженій кімнаті та щільна фотореалістична модель не входять у межі проєкту.

## Докази Промпта 7, 03.11.2026

Глобально `limits.stored_jobs=100` рахує всі записи незалежно від стану, а `queued_jobs=10` залишається окремим pending cap. Count та INSERT виконуються атомарно під PostgreSQL advisory lock; відмова 429 має `stored_job_limit_reached`, `count`, `limit`. Відхилені та часткові uploads прибираються. При count понад cap старі задачі доступні, автоматичного видалення немає.

GET jobs тепер повертає об'єкт із items/total/page/page_size/total_pages/has_next/has_previous/stored_job_limit; типово 20, максимум 100, порядок created_at DESC, id DESC. Невідомі, повторені й невалідні параметри відхиляються. List не читає геометрію або JSONL. Frontend показує ліміт, сторінки й зрозумілу помилку та зберігає відкритий результат під час оновлення списку.

7 нових HTTP/PG тестів та 5 наявних reservation tests пройшли в одноразових схемах PostgreSQL без dispatcher/SLAM: конкурентні POST біля межі дали 202/429 і точний count=2; всі 7 станів, over-cap доступ, пагінація 27 записів (25 з однаковим timestamp), некоректні параметри та cleanup часткового upload перевірено. Frontend build/TypeScript і 6 unit tests успішні. У браузері без POST переглянуто сторінки 20/20/11, новіший і старий справжні результати, preview, refresh та reload.
