# Майбутня архітектура

Це план за Промптом 1. Сервіси, ядро та інтерфейс ще не реалізовані.

```text
Браузер (React / TypeScript / Vite)
  → зовнішній Nginx (HTTPS)
  → API (Python / FastAPI) → PostgreSQL (SQLAlchemy / Alembic)
                              ↑
Dispatcher ← черга задач ──────┘
  → обчислювальний Nginx (load balancer)
  → compute-1 / compute-2 [ / compute-3 при автоматичному розширенні ]
      → окремий процес обчислювального ядра

API та compute-сервери → спільне сховище відео й результатів
Compute / dispatcher → стани, прогрес і посилання на результати → PostgreSQL
```

API перевірятиме вхідні дані й права, створюватиме задачу та надаватиме стан, історію й результати. PostgreSQL зберігатиме користувачів, задачі, обмежену чергу, призначення серверу, прогрес і метадані артефактів; великі відео та результати лежатимуть у спільному сховищі поза Git.

Dispatcher забиратиме готову до запуску задачу з БД і передаватиме її через обчислювальний Nginx на вільний compute-сервер. Призначення фіксуватиметься у БД; повторна доставка не повинна запускати другу копію тієї самої задачі. Кожен сервер прийматиме лише дозволену кількість обчислень, а решта задач чекатимуть у обмеженій черзі. Скасування адресуватиметься серверу, якому вже призначено задачу.

Одна задача оброблятиме кадри свого відео послідовно на одному сервері. Балансувальник розподілятиме між серверами різні задачі, а не кадри одного відео. Базово заплановано 2 окремі compute-сервери, при автоматичному розширенні — максимум 3. Це проєктні налаштування; вихідна умова вимагає щонайменше 2 сервери, але не встановлює максимум 3.

Worker керуватиме окремим процесом готового ядра, реальним прогресом, тайм-аутом і завершенням процесів при скасуванні. Перший кандидат — офіційний ORB-SLAM3 на C++; придатність і залежності потрібно перевірити на наступному етапі. Власний SLAM на підготовчому етапі не пишеться. Результат — оцінена траєкторія та розріджені 3D-точки у відносних одиницях; браузер показуватиме лише дані обчислення.

Docker Compose заплановано для локального підйому сервісів. Для R7 окремий контролер автоматично запускатиме третій compute-сервер за навантаженням, перевірятиме його готовність і оновлюватиме склад upstream обчислювального Nginx. Саме оголошення трьох контейнерів у Compose не доводить автоматичного розширення.

Доказ R5 — дві справжні паралельні задачі через балансувальник із task_id, server_id, часовими мітками та результатами. Доказ R7 — автоматичний запуск третього сервера й реальна обробка на ньому без перевищення максимуму. На поточному етапі цих доказів немає.
