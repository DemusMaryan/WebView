# Майбутня архітектура

Майбутня схема уточнена перед Промптом 2: нативний запуск у WSL Ubuntu, без Docker/Docker Compose/Dockerfile. Поточний етап — лише CV-прототип; PostgreSQL, Nginx, API, dispatcher, HTTP compute-сервіси та вебінтерфейс зараз не встановлюються й не реалізуються.

```text
Браузер (React / TypeScript / Vite)
  → зовнішній Nginx (HTTPS)
  → API (Python / FastAPI) → PostgreSQL (SQLAlchemy / Alembic)
                              ↑
Dispatcher ← черга задач ──────┘
  → обчислювальний Nginx (load balancer)
  → незалежні HTTP compute-1 / compute-2 [ / compute-3 при розширенні ]
      → окремий процес обчислювального ядра

API та compute-сервери → спільне сховище відео й результатів
Compute / dispatcher → стани, прогрес і посилання на результати → PostgreSQL
```

PostgreSQL, зовнішній і обчислювальний Nginx, API, dispatcher та незалежні HTTP compute-сервери запускатимуться нативними сервісами/процесами, локально у WSL. API перевірятиме вхідні дані й права, створюватиме задачу та надаватиме стан, історію й результати. PostgreSQL зберігатиме користувачів, задачі, обмежену чергу, призначення серверу, прогрес і метадані артефактів; великі відео та результати лежатимуть у спільному сховищі поза Git.

Dispatcher забиратиме готову до запуску задачу з БД і передаватиме її через обчислювальний Nginx на вільний compute-сервер. Призначення фіксуватиметься у БД; повторна доставка не повинна запускати другу копію тієї самої задачі. Кожен сервер прийматиме лише дозволену кількість обчислень, а решта задач чекатимуть у обмеженій черзі. Скасування адресуватиметься серверу, якому вже призначено задачу.

Одна задача оброблятиме кадри свого відео послідовно на одному сервері. Балансувальник розподілятиме між серверами різні задачі, а не кадри одного відео. Базово заплановано 2 окремі compute-сервери, при автоматичному розширенні — максимум 3. Це проєктні налаштування; вихідна умова вимагає щонайменше 2 сервери, але не встановлює максимум 3.

Worker керуватиме окремим процесом готового ядра, реальним прогресом, тайм-аутом і завершенням процесів при скасуванні. У Промпті 2 перевіряється офіційний ORB-SLAM3 на C++: спочатку стандартний монокулярний приклад, потім тонкий експортер; власний tracking/mapping не пишеться. Результат — оцінена траєкторія та розріджені 3D-точки у відносних одиницях; майбутній браузер показуватиме лише дані обчислення.

Відтворювані скрипти CV-збирання/запуску зберігатимуться в поточному репозиторії. Великі вихідники ядра й залежностей, build та датасети — у файловій системі WSL поза OneDrive і змонтованим диском C:. Репозиторій не переноситься й не дублюється.

Для R7 окремий контролер має автоматично запускати додатковий сервер за навантаженням, перевіряти готовність і оновлювати upstream обчислювального Nginx; проєктна межа — 3. Спосіб розгортання ще потребує рішення: запуск додаткових процесів на одному вузлі не оголошується гарантовано еквівалентним наведеним у WebProject.txt ВМ/контейнерам. R7 залишається відкритою запланованою вимогою, а не вилучається через відмову від Docker.

Доказ R5 — дві справжні паралельні задачі через балансувальник із task_id, server_id, часовими мітками та результатами. Доказ R7 — автоматичний запуск третього сервера й реальна обробка на ньому без перевищення максимуму, а також підтверджена відповідність способу розгортання умові. На поточному етапі цих доказів немає.
