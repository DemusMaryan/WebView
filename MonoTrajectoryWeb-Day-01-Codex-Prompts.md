# MonoTrajectoryWeb — промпти Codex на день 1

Дата підготовки: 31 жовтня 2026 року.

## Як почати

1. Відкрий у VS Code окрему робочу папку MonoTrajectoryWeb і поклади до неї WebProject.txt.
2. Подавай наведені промпти по одному в одному проєкті. Перший починає підготовку; наступний продовжує перевірений результат.
3. Після промпта 2 перевір результат CV-прототипу. Якщо траєкторії й точок немає, промпти 3–4 залежать від усунення цього блокера.
4. Промпти 3–4 — ціль дня 1 після успішного прототипу. Якщо обчислювальне ядро забрало весь доступний час, зафіксуй результат промптом 5 і скоригуй наступний день. Не замінюй реальний результат заглушкою.
5. Попередні файли CourierRouteLab описують іншу тему й стару Git-політику. Поточні інструкції для MonoTrajectoryWeb мають пріоритет: Codex не відправляє зміни на GitHub.
6. Після кожного етапу користувач може передати звіт Codex на перевірку. Сам факт генерації коду не означає успішного запуску.

## Git та аватарка

Codex створює лише локальні коміти. GitHub-публікацію та будь-який push користувач виконує сам.

Автор коміту визначається не тим, хто натиснув push. GitHub пов’язує коміт з акаунтом за commit email. Потрібна твоя підтверджена email-адреса або точна персональна noreply-адреса зі сторінки GitHub Settings → Emails.

Перший промпт перевіряє також комітера та ефективні значення Git, щоб ідентичність бота не потрапила в нові коміти. Якщо ідентичність не встановлена, Codex продовжує роботу з файлами та повідомляє, які дані потрібні; коміти залишаються невиконаними.

Офіційні пояснення:
- https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address
- https://git-scm.com/docs/git-var

## Промпт 3. Worker, PostgreSQL і базовий API

```text
Прочитай AGENTS.md, WebProject.txt, docs/architecture.md та docs/cv-prototype.md. Виконай тільки базову інтеграцію робочого CV-прототипу з обробкою відеофайла, PostgreSQL і API дня 1. Якщо попередній прототип не працює, не створюй фіктивний compute-сервіс — вкажи блокер.

Збережи існуюче працююче ядро та додай:
1. Один запуск worker на одне відео, з окремим дочірнім обчислювальним процесом. Прогрес і запити скасування не повинні блокувати API.
2. Вхід: відеофайл, ідентифікатор задачі, перевірене калібрування/профіль камери та налаштовані ліміти. Для звичайних відео поясни необхідність параметрів камери; не видавай випадково підібране калібрування за правильне.
3. Декодування відео з часовими мітками. Якщо змінюєш розмір кадру, відповідно зміни intrinsics. Не змінюй калібрування дисторсії довільно. Не пропускай кадри лише заради обіцянки швидкості.
4. Для наскрізної перевірки підготуй короткий відеофайл із перевіреної послідовності попереднього етапу, зберігши коректні параметри камери для його роздільної здатності. Зафіксуй перетворення й джерело. Великі медіафайли не комітяться.
5. Контракт проміжного стану: job_id, server_id, processed_frames, доступна загальна кількість кадрів, stage, tracking_state, актуальна Twc, обмежена кількість точок і траєкторія. Логи ядра відокрем від машинного протоколу. Обмежуй частоту та обсяг знімків.
6. latest snapshot зберігай атомарно; повний фінальний результат — окремо. Поточний оброблений кадр для перегляду має відповідати frame_id знімка. Великі медіа й масиви зберігай у файловому томі, а в БД — метадані й посилання.
7. Настроювані ліміти розміру файла, тривалості/кількості кадрів, роздільної здатності та часу задачі. Початкові значення обери за фактичним прототипом і запиши. Перевірки мають працювати на сервері також під час декодування/обробки, а не тільки за ненадійними метаданими.
8. Реальне завершення дочірнього процесу при скасуванні та перевищенні часу, зі звільненням слота. Черга не включається в ліміт часу виконання.
9. Моделі SQLAlchemy й міграцію Alembic для jobs: UUID, майбутній owner_id, параметри, статус/етап, прогрес, часові мітки, server_id, запит скасування, посилання на результати та помилка.
10. API:
   POST /api/jobs — завантаження відео з параметрами, створення задачі та швидка відповідь з id;
   GET /api/jobs — список збережених задач;
   GET /api/jobs/{id} — стан і метадані;
   GET /api/jobs/{id}/snapshot — актуальні проміжні дані;
   GET /api/jobs/{id}/result — готовий результат;
   POST /api/jobs/{id}/cancel — скасування.
   Файлові шляхи генеруй за job_id; клієнт не може читати довільні файли сервера.
11. Просту персистентну чергу в jobs і окремий dispatcher з одним одночасним запуском для дня 1. Атомарно резервуй задачу та захисти один job_id від повторного запуску. Повноцінне паралельне балансування і ETA перевіримо наступними етапами.
12. Compute HTTP-сервіс для виконання задачі: працює з дочірнім процесом, зберігає реальний стан, має server_id і health endpoint. Обчислювальний HTTP-запит внутрішнього dispatcher може залишатися активним до завершення; браузерний POST не чекає цього.
13. Docker Compose: PostgreSQL зі збереженим томом; API; dispatcher; Nginx; compute-1 та compute-2 з різними server_id; спільний том для вхідних файлів і результатів. Внутрішній обчислювальний шлях dispatcher → Nginx → compute. Для дня 1 достатньо наскрізної перевірки однієї задачі; два health endpoint ще не є доказом повного R5.
14. Авторизацію завершуємо дня 2. Для цього локального прототипу залиш owner_id явно невизначеним і доступ лише через localhost; не видавай це за авторизацію. Не створюй прихований «спільний користувацький акаунт». Запиши необхідну подальшу прив’язку задач до користувача. Публікуй порт входу Nginx на 127.0.0.1 хоста; PostgreSQL і compute не публікуй назовні. Усередині Docker сервісам дозволено слухати контейнерні інтерфейси для взаємного доступу.

Приймання:
- справжнє відео через POST проходить до реального обчислювального процесу;
- API відповідає під час роботи;
- кілька різних snapshot спостерігаються до завершення достатньо довгої задачі;
```
