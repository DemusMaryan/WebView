# MonoTrajectoryWeb

## Джерела та поточний етап

- `WebProject.txt` — головне джерело навчальних вимог. Зберігай вхідні файли та інструкції користувача.
- `MonoTrajectoryWeb-Day-01-Codex-Prompts (1).md` — послідовність початкових етапів; вхідний файл не перейменовуй і не редагуй. Промпти 1–7 завершено в задокументованих перевірках. Для Промпта 6 підтверджено два глобальні слоти, PostgreSQL reservation, Nginx, паралельні валідовані результати та ізоляцію cancel/timeout без залишених PID, включно із zombie. Промпт 7 додав глобальний stored cap 100 окремо від 10 pending, атомарне admission і пагінацію; всі 51 наявна задача збережені. Актуальний контракт і перевірки — `docs/api-contract.md`. Граничні тести виконуються лише в isolated PostgreSQL без dispatcher/SLAM. Наступні функціональні етапи без нового запиту не починай; авторизацію/HTTPS, ETA, масштабування й адмінпанель не реалізовуй.
- Збережи перевірене CV-ядро й залежності з комітів e21d41d, 0bcfe8b, 6332ed4. Узгоджений `-march=native` усуває Eigen ABI mismatch. Не змінюй прапорці, версії чи shutdown і не перебудовуй залежності без конкретної причини. Промпт 3 адаптує відеовхід і підключає наявний runner.
- Збирання й запуск виконуються нативно у WSL Ubuntu. Не перевіряй і не запускай Docker Engine, не встановлюй Docker, не створюй Dockerfile або Compose-конфігурації. Наявні API/UI зберігаються. R5 не позначай перевіреним до двох успішних валідованих результатів із доведеним перекриттям native-процесів та перевірок ізоляції. Документація поточного етапу — `docs/parallel-processing.md`.
- Великі вихідники, залежності, build і датасети зберігай у наявній native файловій системі WSL поза OneDrive. Фізично поточний VHDX лежить на C:, тому вільний простір Windows перевіряється окремо від Linux df; не називай це зберіганням поза C:. VHDX і поточний Git-репозиторій не перенось та не дублюй; власні скрипти, невеликі патчі й документацію зберігай тут. За потреби Python використовуй окреме venv; не змінюй глобальні налаштування Windows/WSL/Git.
- Перед збірками/тестами перевір native FS і backing volume; незмінний резерв C: — 5 GiB. Не змінюй pagefile/hiberfil, не стискай/перенось VHDX і не змінюй його параметри. Початкові 29 задач збережено; не застосовуй до них нове очищення. Лише нові задачі мають `frame-work-policy.json`: після завершення групи процесів прибираються робочі RGB PNG, а опубліковані previews, відео й результати зберігаються. Окремий storage manager не реалізований.

## Тема та межі

Користувач завантажує записане монокулярне відео. Backend послідовно обробляє кадри, зберігає результати й надає справжні проміжні оцінки траєкторії камери та розріджених 3D-точок. Масштаб відносний; без зовнішнього масштабу координати не можна називати метрами.

Живий відеопотік, повторна локалізація у збереженій кімнаті та щільна фотореалістична модель не входять у тему.

## Вимоги та майбутня архітектура

План має охоплювати R1–R8: ліміти; реальний прогрес; історію/стан/скасування/нові задачі з обмеженням кількості й БД; авторизацію/HTTPS; балансування реальних обчислень; обмежену чергу/ETA; автоматичне розширення з верхньою межею; адміністративний моніторинг. HTTPS і R6–R8 дають додаткові бали, але залишаються в плані. Критерії та фактичні статуси — у `docs/requirements.md`.

Стек: Python/FastAPI, PostgreSQL/SQLAlchemy/Alembic, React/TypeScript/Vite/Three.js та Nginx, запущені нативними сервісами/процесами у WSL; браузер доступний через localhost. Docker і Docker Compose не використовуються. Офіційний ORB-SLAM3 (C++) уже перевірено; власний SLAM не розробляй. Для стороннього відео вимагай явне калібрування, не застосовуй TUM автоматично.

Майбутня схема: браузер → API → PostgreSQL; dispatcher → обчислювальний Nginx → незалежні HTTP compute-сервери; спільне файлове сховище. Локально це окремі нативні процеси/сервіси. Одне відео обробляється послідовно на одному сервері, різні задачі розподіляються між серверами. Базово 2 compute-сервери, максимум 3 при автоматичному розширенні — це проєктні налаштування, а не числа з умови. R7 зберігається; відповідність масштабування лише процесами на одному вузлі формулюванню про ВМ/контейнери залишається відкритим питанням.

## Докази та перевірки

- Не вигадуй траєкторію, точки, прогрес, FPS або результати перевірок. Не підміняй обчислення таймером чи штучною затримкою.
- Фіксуй фактичні команди, результати та обмеження. Наявність коду, конфігурації чи двох процесів не доводить виконання вимоги.
- Спочатку запусти стандартний приклад ORB-SLAM3, потім додай тонкий експортер. Вхід — тільки монокулярні RGB-кадри з перевіреним калібруванням, без прихованої глибини/ground truth. Запуск не має вимагати відкритого графічного вікна.
- Експортуй узгоджені справжні пози, tracking state та точки під час обробки; не зберігай сирі посилання на точки між оновленнями карти. Якщо ядро дає Tcw, положення камери у світі визначай через Twc = inverse(Tcw). Втрату tracking позначай явно. Порожній результат не є успіхом.
- Зафіксуй кадри, валідні пози, точки, час і швидкість; збережи фінальні trajectory.json, map_points.json і графік саме з отриманих даних. Відтворювані команди та обмеження запиши у `docs/cv-prototype.md`.
- Для R5 потрібні реальні паралельні обчислення різних задач через балансувальник на двох окремих compute-серверах.
- Майбутні функції позначай «заплановано»; статуси «частково» та «перевірено» потребують конкретних доказів.
- Зберігай секрети, ключі, сертифікати, дані БД, великі медіа/датасети, build і результати запусків поза Git. Невеликі явно підготовлені fixtures можна додавати окремо після перевірки. Lock-файли залежностей комітяться.

## Правила Git

- Створюй лише локальні коміти завершених перевірених змін. Якщо репозиторію немає, спочатку перевір батьківські папки; не створюй вкладений репозиторій. Нова гілка — `main`.
- Перевіряй `git status`, diff та склад змін перед комітом; не включай сторонні зміни без перевірки та не переписуй наявну історію.
- Перевіряй `user.name` і `user.email` із джерелом конфігурації, а безпосередньо перед кожним комітом — `git var GIT_AUTHOR_IDENT` та `git var GIT_COMMITTER_IDENT`. Обидва мають належати користувачу. Перевір можливі перевизначення середовищем; не друкуй токени чи повний дамп середовища.
- Використовуй уже налаштовану ідентичність користувача. Якщо імені/email немає або вказаний бот, продовж роботу з файлами без комітів і повідом, що потрібні точне ім’я та підтверджений email GitHub або точна персональна noreply-адреса з GitHub Settings → Emails. GitHub username не замінює email; не вигадуй адресу й не конструюй noreply самостійно.
- Користувач підтвердив ідентичність `versal217 <versaldata@gmail.com>` для локальних комітів. Перед комітом перевір її ефективність саме в середовищі виконання Git; підтвердження не скасовує цієї перевірки.
- Отримані від користувача дані налаштовуй тільки через `git config --local`; глобальну Git-конфігурацію не змінюй. Не коміть із невирішеним перевизначенням ідентичності середовищем.
- Не додавай бота в `Co-authored-by`.
- Не виконуй `git push`, Publish/Sync, `gh repo create --push`, запис комітів через GitHub API або будь-яке інше відправлення змін на GitHub. Публікацію й push виконує користувач. Читання офіційних репозиторіїв та завантаження залежностей у межах дозволеного етапу дозволені.
- У звіті наводь створені коміти, автора й комітера; якщо комітів немає — причину. Завершуй звіт словами «Push не виконувався».
